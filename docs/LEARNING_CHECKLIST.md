# MedFlow 完整学习清单

适用项目：`E:\code\java\MedFlow`。目标是自己会点、能沿请求找到代码、能解释失败与并发，不以读完文件或背诵注解为通过标准。当前使用 Java 25 / Spring Boot 3.5 / MyBatis / MySQL / 原生 JS；不能照手册示意图说成已经用了 JDK21、Vue3 或微服务。

最新业务口径：患者自己确认预约、自己签到；管理员配置资源；医生只操作自己的接诊。开发状态以 [业务台账](BUSINESS_PROGRESS.md)和最新交付报告为准，[M0审计](00-current-state.md)保留当时的失败快照。

本地参考学习见[尚医通真实源码对照](SHANGYITONG_CODE_COMPARISON.md)与[取舍任务单](SHANGYITONG_ADOPTION_PLAN.md)：同时打开双方方法，解释日期余量、确认凭证、对象权限、幂等取消、信息快照、挂号费/药费和复诊边界。完整后端与患者端已解出；任务单待开发，不照搬微服务，不将其他公开版本或枚举当作本地已实现闭环。

每个勾选项都用四步验收：**手点一遍 → 找到 API/Service/SQL → 解释一次失败 → 关掉代码复述**。建议一轮只学一个业务动作，不要一天同时钻 JWT、行锁和 Redis 全部细节。

## 第一关：先完整使用系统

- [ ] 用 admin、doctor、patient 分别登录，说明三种菜单为什么不同。
- [ ] 区分登录账号、医生档案、就诊人；记下一组 userId/doctorId/patientId，解释它们不能混用。
- [ ] 管理员查看科室、诊室、医生账号映射，发布一场自己的学习排班。
- [ ] 患者按科室或找医生，查看简介、选择日期/时段、选就诊人并提交和确认。
- [ ] 患者查看预约详情及状态历史；在截止前取消一笔预约，观察号源回补。
- [ ] 看清“可预约日期”和“可签到时间”不同：明日预约今天不能签到。
- [ ] 用已签到演示患者走医生开始接诊、保存草稿、完成、患者看病历。
- [ ] 打开同一就诊人的院内档案，比较不同医生、不同日期的记录；切换家属不能混档。
- [ ] 用第二个浏览器会话观察角色切换后的数据变化；一个会话换角色会替换 JWT。
- [ ] 记录一次正常操作和一次规则拦截的截图/错误码，不把虚构诊断当真实医疗建议。

通过标准：离开代码独立演示 10 分钟；能回答每一步由谁操作、修改哪类数据、下一步在哪里。

## 第二关：项目地图、HTTP 与鉴权

先读 `MedFlowApplication`、`pom.xml`、`application.yml`、`SecurityConfig`、`AuthController/AuthService`、`JwtService/JwtAccountValidator/JwtCurrentUserResolver`、`shared/web/Result`、`GlobalExceptionHandler`、`RequestTraceFilter`。

- [ ] 画出 浏览器→Controller→Service→Repository/Mapper→MySQL→响应 的调用链。
- [ ] 在浏览器 Network 找到登录和一次业务请求，识别 method、URL、body、Bearer、响应 code/data、X-Trace-Id。
- [ ] 解释为什么登录公开，业务接口受保护，静态资源可以公开。
- [ ] 解释 BCrypt 的用途，为什么不能在数据库存明文或把密码当 JWT。
- [ ] 解释 JWT 签名、过期时间、uid、role、tokenVersion 的职责；不需要先背 JWT 全部规范。
- [ ] 说明“有 DOCTOR 角色”为什么不能保证“能操作所有 encounter”。
- [ ] 区分 400/401/403/404/409/500，能沿统一错误找到对应业务规则。
- [ ] 解释用户禁用、改角色、改 tokenVersion 后原令牌失效的检查位置。
- [ ] 说明 TraceId 如何从响应头定位日志，为什么日志不应记录病历正文或令牌。

练习：用患者令牌访问医生接口得到 403；不用令牌得到 401；不要修改安全配置使测试通过。

## 第三关：关系模型与资源准备

读 `db/migration/V1–V4/V6/V8/V9`、`OrganizationService`、`DoctorAccountService`、`ScheduleService`、`ScheduleManagementService` 和对应 XML。后续 V11–V14 在相应模块再读。

- [ ] 手画 user→doctor、user→patients、department→doctors/rooms、schedule→slots→appointments→encounter→record。
- [ ] 解释为什么一个账号可以管理多位就诊人，为什么历史按 patientId 聚合。
- [ ] 解释医生开账号和绑定档案同事务，失败时不能留下半套数据。
- [ ] 区分班次模板、排班、号源：模板是规则，排班是某医生某天出诊，slot 是可预约容量。
- [ ] 算一次 08:00–12:00、每段 30 分钟、每段 10 人生成多少 slot、总容量多少。
- [ ] 解释创建草稿和发布分开，发布状态和 slot 插入为什么同事务。
- [ ] 说明批量最多 7 日期，某一天冲突时为什么整个批次回滚。
- [ ] 找出 Doctor→ClinicRoom 锁顺序和排班重叠条件；相邻时段为什么可以、不算重叠。
- [ ] 找出唯一索引、普通索引、CHECK、逻辑关联的区别；如实说当前原迁移没有物理 FK。
- [ ] 解释 Flyway 版本、checksum，为什么不能修改已执行旧脚本。
- [ ] 说明医生职称/擅长/简介如何维护，为什么这类公开资料可以缓存。

练习：用两个请求竞争同医生重叠排班；用真实测试验证，一个成功一个冲突。先理解锁保护哪一行，再讲隔离级别。

## 第四关：预约主链，必须最熟

重点阅读 `AppointmentController`、`AppointmentService`、`PatientService`、`IdempotencyRepository/Mapper`、`SlotBookingService`、`SlotMapper.xml`、`AppointmentMapper.xml`。

- [ ] 按源码写出 create 的顺序：校验归属→幂等记录→锁号源和排班→锁后取 DB 时间→核对可约/重复→条件扣容量→插预约→写历史→存成功结果。
- [ ] 解释为什么不能 SELECT remaining 后在 Java 中减一再 UPDATE。
- [ ] 找到 `remaining_capacity > 0`、OPEN、deadline 条件，说明影响行数为 0 怎样处理。
- [ ] 说明创建就占名额；患者确认不再次扣名额。
- [ ] 区分“同幂等键重试”和“不同 key 重复预约同一 patient/slot”。
- [ ] 解释 request_hash 为什么需要；同 key 改 patientId/slotId 应报什么错误。
- [ ] 解释重复请求返回冻结的哪次结果，为什么之后状态变化仍需另查详情。
- [ ] 解释幂等记录、容量、预约、CREATED 日志为何必须同一个本地事务。
- [ ] 找到业务异常必须越过事务边界的位置；为什么 catch 后直接返回成功会破坏回滚。
- [ ] 找到 active_flag 唯一约束，解释取消后再次预约为什么可行。
- [ ] 区分应用时间、DB 时间、等待行锁前后的时间，解释为什么锁后再取时间。
- [ ] 根据一条真实预约，用自己语言讲清患者确认期限和取消期限。

必须演示的失败：无剩余号、号源关闭、超过截止、非本人就诊人、同 key 改参数、重复预约。每个只沿当前调用链解释，不扩成框架百科。

## 第五关：确认、取消、过期与并发

读 `confirm/cancel/expirePending`、`AppointmentExpirationWorker/Scheduler` 和确认/回补 SQL。

- [ ] 手画预约四状态：PENDING_CONFIRMATION、BOOKED、CANCELLED、EXPIRED。
- [ ] 解释患者确认采用旧状态/截止条件，重复确认为何无新日志、无再次扣减。
- [ ] 解释取消与过期获得迁移执行权后才归还一次，不能只看前端按钮是否禁用。
- [ ] 讲清 Slot→Appointment 锁顺序，为什么取消/签到/超时不能各锁各的。
- [ ] 两个取消、取消和过期、确认和过期竞争时，列出允许结果及不允许结果。
- [ ] 解释回补上限检查的用途；为什么“不会加到负数/超过总量”仍不足以保证业务恰好一次。
- [ ] 找到每笔超时处理的事务边界，说明一笔失败不应让后续全部饥饿。
- [ ] 解释 keyset/游标扫描和简单第一页扫描的差别，只结合项目实际实现。
- [ ] 在隔离测试中注入状态日志失败，验证状态/库存一起回滚。
- [ ] 能看懂死锁测试的两个事务等待关系，说明统一锁顺序解决什么、不能保证什么。

证据边界：当前容量实验是 500 个不同就诊人、同一个 owner、竞争 50 个名额、32 连接池；不是线上 500 QPS，也不是 500 个不同账号同时 HTTP。讲指标必须附实验条件。

## 第六关：签到、医生接诊、病历与历史

读 `EncounterService`、`EncounterMapper.xml`、`patient/history/PatientHistoryService` 及 XML，配合 `clinical.js/patient-history.js`。

- [ ] 解释 Appointment 预订资源，Encounter 记录实际就诊，为什么不把所有状态合成一列。
- [ ] 找到签到当天及时间窗口判断；说明页面可签到只是提示，后端仍需复核。
- [ ] 重复签到应返回同一 encounter；解释唯一 appointment_id 和事务锁各自保护什么。
- [ ] 列出 WAITING→IN_PROGRESS→COMPLETED 及 WAITING→SKIPPED 合法迁移。
- [ ] 解释一个医生同一时间只接诊一人，医生行锁和生成列唯一键如何配合。
- [ ] 说明病历四字段、草稿版本、保存与完成的区别；过期版本为何 409。
- [ ] 解释草稿为什么患者看不到，完成后为什么不能再直接编辑。
- [ ] 解释完成/过号不归还已消耗时段容量。
- [ ] 解释同一患者不同医生的历史如何聚合；同账号家属为什么要再次 patientId 校验。
- [ ] 解释医生历史 anchor 是什么，不能只传随便一个 patientId 读全库。
- [ ] 说明本教学版历史授权简化规则和未做跨院/检查/影像，不宣称完整 EHR。
- [ ] 页面填写未保存病历后打开历史，应提示保存；返回当前接诊继续操作。

通过标准：手动完成一个接诊；向另一个人解释“历史只读”和“本次病历编辑”为什么走不同接口。

## 第七关：可选业务与 Redis 亮点

先掌握前六关；下面按现有代码学习，不再为了简历增加 MQ/微服务。

药品、处方和模拟缴费：

- [ ] 读 `DrugService` 和 `PrescriptionService`，区分药品目录价格和处方价格快照。
- [ ] 说明一接诊一处方、一处方一账单、一账单一模拟支付的唯一约束。
- [ ] 解释 DRAFT→ISSUED 冻结、DISCARDED 草稿放弃，版本检查与重复操作。
- [ ] 用 BigDecimal 验算数量×单价、总金额，解释不能用浮点金额。
- [ ] 说明待完成处方草稿为何阻止结束接诊，患者不能为他人账单缴费。
- [ ] 手动完成一次模拟缴费并重复点击；明确没有真实扣款、药房库存或医保。

Redis 医生详情，六项都能自己解释：

- [ ] 第一次 GET：Redis miss→MySQL→回填；第二次 hit，如何证明没有重复查 MySQL。
- [ ] 用 Redis CLI 查 key/value/TTL，区分正常值 TTL 与空值 TTL。
- [ ] 不存在 ID 为什么要短期空值缓存；为什么数据库故障不能缓存成“不存在”。
- [ ] 修改资料为什么先提交 MySQL，再删缓存；回滚不能删，怎么验证 afterCommit。
- [ ] Redis 停机时的超时、退避、MySQL 降级；不能笼统说“Redis 故障不影响任何业务”。
- [ ] 解释缓存失效失败的本节点绕过与 TTL 边界；承认缓存旁路仍有并发旧值回填窗口。
- [ ] 说明为什么没有把号源扣减或病历当这个缓存案例的扩展对象。

统计：读 `StatisticsRepository/Service`，说明预约创建时间趋势、完成时间的科室/医生工作量是不同口径，日期补零与半开区间有什么用。

## 第八关：前端、部署、测试与面试证据

- [ ] 读 `api.js`：请求封装、JSON 信封、超时、401、切角色后迟到响应处理。
- [ ] 读 `booking.js`：上游选择变化清下游，异步 ticket 防串，空态和失败重试。
- [ ] 读 `app.js openBooking`：幂等键何时复用、患者切换时如何区分、结果不确定时如何核对。
- [ ] 解释禁用按钮不等于后端幂等；UI 数据脱敏和 XSS 转义为什么仍需要服务端权限。
- [ ] 用 Network 找到从点科室到提交预约的全部请求，说明哪个是读、哪个是写。
- [ ] 解释为什么一页预约的日期/医生摘要一次批量读取，而不为每一行单独发一个请求；摘要加载失败不能伪装成预约不存在。
- [ ] 读 Dockerfile/Compose：为什么前后端一个 JAR、mysql 服务名、宿主端口、持久卷和缓存可丢失。
- [ ] 找到 `.env` 注入位置，说明启动/停止/备份/回滚，知道 down 与 down -v 不同；不要为演示清空原卷。
- [ ] 区分单测、MVC、真实 MySQL IT、HTTP、浏览器人工验收，不把 mocks 当真实数据库。
- [ ] 自己运行一组针对性测试，定位一次失败，不通过时保留证据，不删断言冒充修复。
- [ ] 解释演示 registry 为什么不在重启时把已缴费改回未缴费、已完成改回候诊。
- [ ] 写一页“已实现/已测试/未实现/可选扩展”，与业务台账核对。
- [ ] 不看代码讲 5 分钟项目、10 分钟预约一致性、5 分钟 Redis；回答追问而不是背稿。

推荐顺序按理解产出安排，不保证固定两天吃透：第一轮主线（第一至六关），第二轮故障与工程化（第四/五/八关），第三轮扩展与面试（第七关和全链复述）。每天 6 小时也要留操作和复述时间；开发压缩到两天不代表学习必须压缩到两天。

## 最终自测：这些问题应能脱稿答

1. 为什么医生账号、医生档案、就诊人不是同一张表？
2. 如果最后一份容量被两个事务同时抢，凭什么只成功一个？
3. 相同幂等键和有效预约唯一索引分别防什么？
4. 创建扣容量后插入日志失败会怎样？谁触发回滚？
5. 患者确认为什么不再扣容量？超时与取消怎么防止多退？
6. 签到和取消同时发生如何保证结果合理？
7. 为什么完成就诊后预约还是 BOOKED？
8. 为什么医生甲能读患者乙的历史，却不能编辑别的医生病历？入口和条件是什么？
9. 为什么 Redis 更新在事务提交后删？Redis 停机和 MySQL 停机处理是否一样？
10. 为什么这个项目选择单体？哪些复杂功能明确没做？
11. 怎么在新机器空库启动？本次测试证据与生产经历有什么区别？
12. 展示你自己点出来的一笔预约、一次失败、一条完整病历、一张模拟账单和对应请求日志。
