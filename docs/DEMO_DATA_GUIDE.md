## 账号与入口

Docker Compose 本机演示模式同时开启 `MEDFLOW_DEMO_ACCOUNTS_ENABLED=true` 和 `MEDFLOW_DEMO_WORKFLOW_ENABLED=true`：前者准备三个演示账号，后者补齐整套业务数据。应用升级启动、Flyway迁移完成后执行；普通本地启动的业务演示补齐默认关闭，仅开账号开关不会自动生成业务样例。

| 角色 | 用户名 | 密码 | 登录后的主要入口 |
| --- | --- | --- | --- |
| 管理员 | `admin` | `123456` | 门诊工作台、排班与发布、药品目录、业务统计 |
| 医生 | `doctor` | `123456` | 医生工作台、我的排班、预约患者、候诊与接诊 |
| 患者 | `patient` | `123456` | 就诊工作台、预约号源、我的预约、就诊人、处方与缴费 |

新增目录医生（均为虚构，密码同为`123456`）：`demo.internal`对应林医生/演示内科，`demo.surgery`对应周医生/演示外科，`demo.derm`对应陈医生/演示皮肤科。主账号`doctor`的既有科室绑定和姓名保留，不强制改成新增目录医生。

默认访问 [MedFlow](http://127.0.0.1:8080/)。若修改应用端口，使用启动脚本显示的实际地址。启动、停止、保留 `.env` 和升级命令见 [Docker使用说明](DOCKER.md)，完整业务操作见 [前端指南](FRONTEND.md)。

**医生排班由管理员分配，不需要医生报名。** doctor是登录用户名，页面中的医生姓名是与其绑定的档案名称；新库通常为“演示医生 / 演示门诊”，已有有效科室和姓名绑定会保留。不要再次创建同名账号或重复绑定，也不要仅凭姓名猜测账号身份。

## 补齐内容与保留规则

演示初始化以数据库的业务日期为准，按日期和标记幂等补齐缺少的虚构记录，不清空旧库、不删除正常数据，也不把已经操作过的种子恢复为初始状态。

| 演示内容 | 用途与边界 |
| --- | --- |
| doctor所属科室、演示诊室 | 优先保留现有医生科室绑定，缺少相应演示资源时补齐；诊室名称带“虚构”标识 |
| 明日起未来7天排班与号源 | 上午08:00–12:00、下午13:00–17:00的已发布示例；已有医生/诊室冲突时安全跳过，不覆盖真实安排 |
| 更后一天的草稿示例 | 管理员查看草稿、检查详情并练习发布；冲突时可能不新增 |
| 今日候诊、已完成与过号记录 | 默认准备2位待就诊、2位已完成、1位过号的虚构示例；不预占“就诊中”，便于医生练习开始接诊 |
| patient名下的虚构就诊人和预约 | 包含今日各接诊状态及未来预约示例；不混入其他患者账号的资料 |
| 已完成病历 | 四字段明确标记为模拟内容，供患者查看结果、医生查看只读记录 |
| 演示药品与已提交处方 | `DEMO-`编码的示例目录；两份已完成记录配有处方，分别演示待缴费与已模拟缴费账单 |
| 模拟支付记录 | 已缴费账单有唯一模拟登记，无真实扣款；重复初始化不重复支付 |

上表是补齐逻辑的目标样例，当前页面数量受既有资源冲突和已发生操作影响，不能作为每次刷新后的固定数量承诺。药品、病历、用法和账单只供软件演示，不用于真实诊疗。

**今日已签到、已完成和已模拟缴费记录由虚构种子直接准备，不代表真实患者曾到院、医生曾开药或发生支付。** 自己通过正常页面创建的新预约仍须按真实业务规则：先确认、在就诊当天规定窗口签到、到时段开始后接诊。

## 管理员：查看资源与补齐演示数据

1. 登录 `admin`，进入「门诊工作台」。演示账号和业务补齐两个开关均开启时，出现「本机演示数据」区域和「补齐演示数据」按钮。
2. 点击按钮补齐当前日期缺少的数据。请求过程中按钮不可连点；成功后重读概览，失败会显示错误并允许重试。此操作不重置已取消预约、已完成/已过号接诊或已缴费账单。
3. 进入「排班与发布」，选择今天到未来7天的范围、doctor所属科室和医生，查看已发布安排及真实号源详情。要找草稿时适当扩大日期范围或选择“草稿”状态。
4. 在「药品目录」搜索 `DEMO-` 查看示例药品、价格和启用状态。修改价格只影响以后保存草稿取得的价格快照，不改写已提交处方。
5. 在「业务统计」查看近7天预约创建趋势、科室已完成接诊量和医生工作量；这些是数据库中的实际聚合，包含明确标识的演示记录，不是医院真实经营数据。

补齐接口是 `POST /api/v1/admin/demo-data/refresh`，仍需管理员身份。公开的 `GET /api/v1/auth/demo-config` 仅返回 `enabled`、`workflowEnabled` 开关，不返回账号秘密，也不授予初始化、查看病历或代缴权限。任一开关关闭或配置读取失败时不显示补齐按钮；普通手动业务照常使用。

## 医生：从今日队列练习接诊

1. 退出管理员，登录 `doctor`。在「我的排班」查看本人未来安排；无需报名、认领或重新绑定。
2. 「预约患者」和「候诊与接诊」默认查询今天；如果要看明天的患者，必须把查询日期改为明天。只显示绑定给当前登录医生的数据。
3. 在今日队列选择一个“演示·候诊…”虚构患者，打开并开始接诊。正常开始操作仍校验时段已开始，且本人同时最多一位就诊中患者。
4. 填写并保存模拟病历。需要练习开方时点击「处方与收费」，选择启用药品、填写数量和用法，保存并核对后端计算金额，再提交生成账单。
5. 不需要已经保存的处方草稿时，明确选择放弃。处方仍为DRAFT时不能完成接诊；已提交、已放弃或无处方均可完成，患者是否缴费不阻止完成。
6. 已完成的种子记录可用来查看只读病历与处方；过号在当前版本为终态，不提供补叫。

如果种子的待就诊患者已经被你处理，重复补齐不会把其改回WAITING。若本人已有一条正在处理的接诊，先完成它，再开始下一人；演示补齐不会强制结束你的工作。

## 患者：明日挂号与处方模拟缴费

1. 退出医生，登录 `patient`。在「就诊人」查看已标记“虚构”的演示档案；也可以另建虚构档案练习。
2. 进入「预约号源」，先选择科室和医生并阅读职称、擅长、简介；也可以从“找医生”按姓名/擅长搜索。选定医生后默认明天，再选日期、上午/下午有余量的时段和就诊人。后续返回页面可能保留选择，请核对日期。
3. 创建后及时确认预约；可在「我的预约」找到真实记录。明天的预约不能今天签到。查看今日种子预约时，使用「签到 / 就诊结果」查看其已有状态，不需要重新签到。
4. 签到窗口是就诊当天 `[时段开始前30分钟, 时段结束)`；自己创建的预约必须符合该规则。演示种子不会让普通接口绕过时间和所有权校验。
5. 在「处方与缴费」查看本人已提交处方：选待缴费示例练习模拟缴费，选已缴费示例查看金额、状态和登记时间。
6. 勾选确认后点击「确认模拟缴费」。这只写入本系统模拟记录，没有真实扣款。重复点击/刷新后再次请求不会产生第二条模拟支付记录。

7. 「就诊人」点姓名或“查看就诊档案”，打开“演示·候诊一（虚构）”：包含林医生、周医生两次已完成历史，可查看四项病历正文、药品明细和账单。医生从本人预约/队列的该患者入口也能只读这些历史。不同家属独立成档，管理员没有默认病历阅读权限。

管理员在「医生」的“维护资料”编辑公开简介。保存后患者重新读取应看到新资料，原有缓存于事务提交后失效。启动仅补齐缺失的演示简介，不覆盖你的后续修改。

午夜至首场出诊前，种子不会插入未来时间的签到/接诊；稍后管理员补齐即可。夜间仍能预约未来日期和阅读已完成历史。今日队列数量取决于时刻和你已经处理的记录，不承诺每次都固定为两位待诊。

处方提交后即可对所属患者可见，即使医生尚未完成接诊；病历正文仍须完成后才能查看。未提交或已放弃的处方不会在患者页面出现。

## 日期变化、旧数据与常见疑问

| 现象 | 处理 |
| --- | --- |
| 登录后没有完整演示样例 | 确认已运行包含本次初始化逻辑的新镜像，且演示配置开启；管理员工作台可手动补齐。旧镜像只包含旧初始化能力。 |
| 隔天登录今日队列为空 | 新版本启动或点击补齐后按数据库当天补样例；此前日期的记录会保留，可切换查询日期查看。 |
| 某天没有预期排班 | 可能有既有医生/诊室冲突，被安全跳过；查看实际目录，换日期或由管理员安排。 |
| 有示例预约但看不到可约时段 | 可约列表仅显示尚未截止且有容量的时段；默认选明天，勿把今日已使用时段当作新号源。 |
| 点补齐后完成记录没有变回候诊 | 正常。补齐不回滚业务状态，不恢复已消耗名额，不重复创建同日相同种子。 |
| 为什么既有科室/姓名没有变为演示默认名 | 为保留原doctor档案绑定，补齐优先使用既有有效资料，而非强行搬迁或重命名。 |
| 想清空重新演示 | 本按钮不清库。使用另一个未处理示例、查询新的日期或手动创建虚构业务，不把日常启动/补齐当作重置。 |

业务边界和接口见 [处方与统计需求](PRESCRIPTION_STATISTICS_REQUIREMENTS.md)，本轮状态统一见 [业务台账](BUSINESS_PROGRESS.md)。本指南描述功能和使用方法，不替代真实环境的启动、迁移、浏览器及权限验收记录。
