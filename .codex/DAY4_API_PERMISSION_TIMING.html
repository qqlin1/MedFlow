确认一

外键立场：用一句话说清 MedFlow 要不要建外键约束，为什么；关联列怎么处理。

不记得理由了？点开看参考答案

立场一句话：不在数据库层建外键约束，关联关系由应用层的校验和事务保证； 所有关联列都建普通索引。

四条理由（从强到弱）

  1. 外键带来你看不见的锁。写子表时数据库偷偷给父表那一行加共享锁， 共享锁持有到事务 COMMIT 才释放（两阶段锁）→ 热点行的锁窗口被拉长 → 并发下降。 更糟的是这些锁查不出来：SHOW ENGINE INNODB STATUS 里指向的是一条你根本没写过的 SQL。
  2. 级联不理解业务规则，会静默破坏数据。ON DELETE CASCADE 下误删一个号源， 几十条预约静默消失，没有校验、没有日志。而按业务规则，有有效预约的号源根本不该被删。
  3. 拖累迁移和批量操作。批量修数据得先 SET FOREIGN_KEY_CHECKS = 0 —— 这个操作本身就说明外键在碍事。将来分库分表，跨库外键根本没法用。
  4. 业界规范。阿里 Java 开发手册：不得使用外键与级联，一切外键概念必须在应用层解决。 但只背这一条不算懂，能说清前三条才算。

代价 + 怎么补
失去数据库的引用完整性兜底 → 靠 ① 应用层写入校验 ② 删除前检查 ③ 定期巡检孤儿数据 ④ 业务上用逻辑删除（医疗数据要留痕）来补。

最值钱的一句（面试加分）
应用层其实做得更好 —— decreaseIfAvailable 的 WHERE id = ? AND status = 'OPEN' AND remaining_capacity > 0 不只检查"号源存在"，还检查"状态开放且还有余量"。 外键只能检查存在，做不到后者，因为它不理解业务状态。

关联列：全部建普通索引。
顺手检查：slot_id 在 uk_patient_slot_active (patient_id, slot_id, active_flag) 里排第二，按最左前缀，单独按 slot_id 查询用不上它，需要单独建 idx_slot。

过关标准：能说出「不建外键约束、关联列建索引」这个立场， 并给出至少一条理由。只说"不建"不给理由 = 不过关。
满分标准：能说出"外键偷偷给父表加共享锁 + 锁窗口被拉长"， 以及"decreaseIfAvailable 已经做了外键想做的事、而且做得更好"。

确认二

复述预约的 4 个事件名单（注意是事件，不是状态）。

过关标准：4 个事件是确认、取消、超时、完成就诊。 5 个状态是待确认、已确认、已取消、已关闭、已完成。 不要说成"已超时"——那是状态不是事件。Day 2 曾在这里错过一次。

知识一：401 / 403 / 409

服务器拿到一个请求，依次过四关。每一关挡下来，返回的状态码都不一样：

码一句话真正含义
401你谁？没认证 —— 没带 Token，或 Token 过期 / 无效
403我知道你是谁，但不行认证通过了，但权限不够
409你没错我也没错，但现在做不了请求合法，但和资源当前状态冲突
401 的名字是个坑。401 Unauthorized 字面是"未授权"，听起来像权限问题， 但它实际表示"未认证"。这是历史遗留的命名错误。 记住 401 = 未认证，403 = 未授权，就不会混。

进阶判断一：403 还是 404？

张三请求查看李四的预约（GET /appointments/5002，那是李四的），返回什么？

  • 返回 403 → 等于告诉对方"这个 id 存在，只是你没权限"。若 id 自增可猜， 攻击者能一个个试，把全库预约 id 枚举出来。这叫 ID 枚举 / IDOR 信息泄露。
  • 返回 404 → 不泄露。但用户困惑（"我明明有这个预约"）， 自己排查时也分不清"真不存在"和"没权限"。
折中做法（推荐）：对外返回 404，日志里记 403。 攻击者拿不到信息，你排查时有据可查。
判断标准：这个 id 是不是连续可猜的、资源是否存在算不算敏感信息。是 → 用 404 伪装。

进阶判断二：400 还是 409？

  • 400 Bad Request —— 请求本身有问题：缺必填参数、格式错、类型不对。 改请求就能解决。
  • 409 Conflict —— 请求没问题，但和资源当前状态冲突。 改请求没用，得等状态变化。

MedFlow 里 409 的四种场景：号源已满 / 已有有效预约 / 状态不允许这个操作（想取消已完成的）/ 幂等记录还在 PROCESSING（上一次请求还在处理中）。

口诀：「改请求有没有用？」有用 → 400；没用 → 409。

知识二：DTO / VO

先说清楚三个东西分别是什么：

名字是什么用在哪
Entity和数据库表一一对应的对象，字段跟表字段一致只在 DAO 层和数据库打交道
DTOData Transfer Object，接口之间传数据的对象Controller 的入参和出参
VOView Object，专门给前端看的对象Controller 的出参（强调"展示形状"）

为什么不能直接用 Entity 接收请求 / 返回响应？四个理由，第一条最要命：

1. 安全问题（最要命）。Entity 有表的全部字段。如果用 Entity 直接接收请求， 前端在 JSON 里多塞一个 "status":"BOOKED"，就能直接把预约状态改成已确认 —— 绕过所有业务校验。这叫 批量赋值漏洞（Mass Assignment）。 用 DTO 接收入参，前端传什么字段都白搭，因为 DTO 里根本没有那个字段。
  • 2. 耦合：改表结构会直接破坏接口契约，前端跟着炸。
  • 3. 字段对不上：接口要显示医生姓名，但表里只有 doctor_id。
  • 4. 校验位置：DTO 上可以加 @NotNull @NotBlank，参数校验有地方安放。

知识三：事务边界

事务该画在哪一层？

Service 层。不是 Controller，也不是 Mapper。
  • 为什么不在 Controller？Controller 负责 HTTP 协议（解析请求、拼响应）。 同一个业务可能被多个入口调用 —— HTTP 接口、定时任务、消息消费者。 事务要跟着业务走，不是跟着 HTTP 走。
  • 为什么不在 Mapper？一个业务操作经常要改多张表。 Mapper 只有单表操作，它不知道"这几张表要一起成功或一起失败"。

MedFlow 创建预约的事务边界

@Transactional                       ← 事务从这里开始
public Appointment book(BookCommand cmd) {
    idempotencyMapper.insertAndGet(...)  // ① 写幂等记录
    slotMapper.decreaseIfAvailable(...)  // ② 扣号源
    appointmentMapper.insert(appt)       // ③ 插预约
    idempotencyMapper.markSuccess(...)   // ④ 改幂等记录为 SUCCESS
    return appt;
}                                        ← 到这里提交或回滚

这四步必须原子：任何一步失败，前面已经做的都要撤销。否则就会出现 "号源扣了但预约没建成"或者"预约建成了但幂等记录没写"这类事故。

事务里绝对不能做的事：外部网络调用。发短信、调支付、直连 MQ 发消息 —— 都不行。

原因直接回扣你学过的一个概念：锁窗口。事务每多停留一秒， 它持有的行锁就多攥一秒，后面排队的请求就多等一秒。网络调用的耗时不可控（可能 30 毫秒，也可能 30 秒）， 把不可控的东西放进事务，等于把系统的并发能力交给网络。 连接池被打满 → 雪崩。

正确做法：Outbox —— 把要发的消息当数据写进本地表（同一个事务）， 事务提交后由后台任务去发。（这是路线四的内容，M4 才动手，现在只要知道为什么。）
