MedFlow 表与索引设计练习表

从业务规则推导索引 — 填写内容自动存在本机浏览器，关掉再开还在

核心命题

每一条唯一索引，都是一句业务规则的翻译。

每一条普通索引，都是一次查询路径的固化。

你不是在建索引，你是在把业务规则钉进数据库。

索引不是技巧问题，是「你有没有把业务规则想清楚」的问题。字段不是自己设计的，就永远只能背索引语法，说不出它为什么存在。

第一部分：推导框架

A. 推唯一索引 — 从规则推，问三个问题

#问题答案长什么样
①约束谁？主体字段（patient_id / user_id / doctor_id）
②在多大的范围里？边界字段（slot_id / schedule_id / work_date）
③什么情况下这条规则不算数？状态 / 有效性字段（active_flag / status）
第 ③ 问最容易漏，也最值钱。业务规则几乎都有时效性：「不能重复预约」通常是「不能重复有效预约」，取消过的、超时的是允许重复的。漏了第 ③ 问 → 用户取消一次就永远约不了了。

B. 推普通索引 — 从查询推，方向相反

  1. 这张表上会发生哪些查询？（翻接口清单，一个一个列）
  2. 每个查询的 WHERE / ORDER BY 里有哪些字段？
  3. 这些字段按什么顺序排？
最左前缀不用背，它是第 ③ 问的副产品：联合索引 (a, b) 能加速 a、能加速 a + b，不能加速单独的 b。所以字段顺序由查询决定，不是按字母排、也不是按重要性排。

C. 校验

每个索引都必须能回答「它在防什么、或在加速什么」。答不上来的，删掉。多余索引会拖慢写入，还会让 UPDATE 多锁不必要的行。

第二部分：完整示范 — med_appointment

第一步：把业务规则写成中文（从需求文档抄）

  • E-03：不同键重复预约 → Service 预检查和数据库唯一约束共同阻止重复有效预约
  • 状态机：PENDING_CONFIRMATION / BOOKED / CANCELLED / EXPIRED
  • 取消与超时都要归还号源（说明取消、超时后该号源可以被重新预约）

提炼成一句：同一个就诊人，在同一个号源上，最多只能有一条处于有效状态的预约。

第二步：问三个问题

① 约束谁？
就诊人 —— 注意不是登录账号，因为可以给家人挂号
→ patient_id
② 在多大的范围里？
这个号源。slot_id 本身已含「某医生 + 某天 + 某时段」，不用再加 doctor_id / work_date
→ slot_id
③ 什么情况下这条规则不算数？
已取消 CANCELLED、已超时 EXPIRED
→ active_flag

第三步：落成索引

ALTER TABLE med_appointment
  ADD COLUMN active_flag TINYINT
      AS (CASE WHEN status IN ('PENDING_CONFIRMATION','BOOKED') THEN 1 ELSE NULL END) VIRTUAL,
  ADD UNIQUE KEY uk_patient_slot_active (patient_id, slot_id, active_flag);

为什么用生成列 + NULL：MySQL 没有部分唯一索引（不能写 WHERE status IN (...) 的唯一索引），但它允许唯一索引里出现多个 NULL。已取消 / 已超时的行 active_flag = NULL → 不参与唯一性判断。

第四步：推普通索引（从接口清单）

查询从哪来SQL索引
GET /appointments 我的预约列表WHERE patient_id = ? ORDER BY created_at DESC(patient_id, created_at)
超时关闭定时任务WHERE status='PENDING_CONFIRMATION' AND confirm_deadline < NOW()(status, confirm_deadline)
GET /doctor/appointmentsWHERE doctor_id = ? AND work_date = ?需冗余这两个字段才能建
冗余字段的判断标准：如果一条查询会被高频执行，而它需要的字段在另一张表上，就在本表冗余一份（插入时带过来，不可变），为的是能建索引。这个取舍本身就是面试故事：愿意为保证业务规则 / 查询性能付出存储代价，而不是把校验甩给应用层。

第三部分：练习 — 8 张表

每张表按三步填：① 写出业务规则（中文一句）② 问三问，得出唯一索引 ③ 列查询，得出普通索引

第四部分：自检

  1. 每条唯一索引，你都能说出它对应的那句中文业务规则 —— 说不出就是多余的
  2. 每条唯一索引，你都认真回答过第 ③ 问（什么情况不算数）—— 漏了就会出「取消后永远约不了」这类 bug
  3. 每条普通索引，你都能说出它服务哪条查询 —— 说不出就是多余的
  4. 每个联合索引的字段顺序，你都能说出为什么是这个顺序（最左前缀）
  5. 你能指出哪些业务规则索引管不了（比如时间重叠判断），并说出替代方案
第 5 条最难，也最值钱。能说出「这个约束我管不了，所以用了别的办法」，比能背出十个索引语法强得多。
