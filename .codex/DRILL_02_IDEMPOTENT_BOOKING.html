第一部分：表结构（三张表，完整定义）

表 1：幂等记录表 sys_idempotency_record

CREATE TABLE sys_idempotency_record (
  id              BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id         BIGINT       NOT NULL,
  operation_type  VARCHAR(32)  NOT NULL,
  idempotency_key VARCHAR(64)  NOT NULL,
  status          VARCHAR(16)  NOT NULL,   -- 取值只有两种：PROCESSING / SUCCESS
  result_json     TEXT,                    -- 成功时缓存的业务响应
  UNIQUE KEY uk_user_op_key (user_id, operation_type, idempotency_key)
);

表 2：号源表 med_slot

CREATE TABLE med_slot (
  id                 BIGINT PRIMARY KEY,
  work_date          DATE         NOT NULL,
  total_capacity     INT          NOT NULL,   -- 总容量
  remaining_capacity INT          NOT NULL,   -- 剩余容量
  status             VARCHAR(16)  NOT NULL    -- 取值：OPEN / CLOSED
);

表 3：预约表 med_appointment

CREATE TABLE med_appointment (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  patient_id  BIGINT      NOT NULL,
  slot_id     BIGINT      NOT NULL,
  status      VARCHAR(32) NOT NULL,  -- PENDING_CONFIRMATION / BOOKED / CANCELLED / EXPIRED
  active_flag TINYINT AS (
      CASE WHEN status IN ('PENDING_CONFIRMATION','BOOKED') THEN 1 ELSE NULL END
  ) VIRTUAL,
  UNIQUE KEY uk_patient_slot_active (patient_id, slot_id, active_flag)
);

第三部分：后端代码

Service 方法

@Transactional
public Appointment book(BookCommand cmd) {
    IdempotencyRecord rec;

    // 第 1 步：往幂等记录表插一条 PROCESSING 记录
    try {
        rec = idempotencyMapper.insertAndGet(cmd.userId(), "BOOK", cmd.requestId());
    } catch (DuplicateKeyException e) {
        // 第 2 步：插入失败 = 有人先插过同一个 key，回查那条记录
        rec = idempotencyMapper.selectForUpdate(cmd.userId(), "BOOK", cmd.requestId());

        if (rec == null) {
            rec = idempotencyMapper.insertAndGet(cmd.userId(), "BOOK", cmd.requestId());
        } else if ("PROCESSING".equals(rec.getStatus())) {
            throw new ConflictException("处理中");
        } else {
            return deserialize(rec.getResultJson());
        }
    }

    // 第 3 步：扣减号源
    int rows = slotMapper.decreaseIfAvailable(cmd.slotId());
    if (rows == 0) throw new SoldOutException();

    // 第 4 步：插入预约记录
    Appointment appt = new Appointment(cmd.patientId(), cmd.slotId(), "PENDING_CONFIRMATION");
    appointmentMapper.insert(appt);

    // 第 5 步：把幂等记录改成 SUCCESS 并缓存结果
    idempotencyMapper.markSuccess(rec.getId(), toJson(appt));
    return appt;
}

第 3 步那条 SQL（decreaseIfAvailable）

UPDATE med_slot
   SET remaining_capacity = remaining_capacity - 1
 WHERE id = #{slotId}
   AND status = 'OPEN'
   AND remaining_capacity > 0

这条 SQL 的返回值是「受影响行数」：扣减成功返回 1，没扣成返回 0。

第四部分：发生的事件

用户张三登录了系统。系统里有两条关于他的数据：

  • 登录账号 user_id = 1001
  • 就诊人 patient_id = 2001（就是张三本人）

张三在前端页面点击「确认预约」按钮，约的是号源 88。

前端的行为：点击那一刻，前端生成了一个字符串 requestId = "REQ-AAA"， 作为这次预约的唯一标识发给后端。因为网络卡顿，前端等了 3 秒没收到响应， 触发了超时重试机制——于是前端用同一个 requestId 又发了一次请求。

结果：服务器几乎同时收到了两个 HTTP 请求，参数完全一样：

请求userIdpatientIdslotIdrequestId
请求 P（第一次点击）1001200188REQ-AAA
请求 Q（前端超时重试）1001200188REQ-AAA

两个请求各自开启一个数据库事务，各自执行上面那段 book 方法。

第五部分：答题前，先确认这些背景事实

下面五条是事实陈述，不是答案。如果你对哪一条不熟悉，先把它看懂再开始答题。

事实 1 · 1062：往一张表插入数据时，如果违反了这张表的唯一索引（要插的值组合起来已经存在）， MySQL 会报错，错误码是 1062 Duplicate entry。 在 Spring 里它表现为 DuplicateKeyException。

事实 2 · 1205：一条 SQL 要修改某一行，但那一行正被另一个还没提交的事务锁着， 这条 SQL 就得排队等。等的时间超过 innodb_lock_wait_timeout（默认 50 秒） 就会报错，错误码是 1205 Lock wait timeout exceeded。

事实 3 · 锁什么时候释放：事务对某一行加的锁，要到这个事务提交（COMMIT）或回滚（ROLLBACK）时才释放， 不是那一条 SQL 执行完就释放。这叫两阶段锁协议。

事实 4 · 快照读与当前读：MySQL 默认隔离级别是「可重复读 RR」。 在同一个事务里，普通的 SELECT 叫快照读，它读的是这个事务第一次执行 SELECT 那一刻 拍下的数据快照——之后别的事务提交了什么新数据，它都看不见。 而 SELECT ... FOR UPDATE 叫当前读，它绕过快照，直接读数据库此刻最新的数据。

事实 5 · 只回滚那一条语句：一条 SQL 报错时，MySQL 默认只回滚报错的那一条语句， 整个事务还活着。只有死锁（错误码 1213）才会让 MySQL 回滚整个事务。
