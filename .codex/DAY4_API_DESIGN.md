## 2. 状态码约定

| 码 | 含义 | MedFlow 场景 |
|---|---|---|
| 400 | 请求格式烂 | slot_id 传了 "abc"，业务未进 |
| 401 | 不知道你是谁 | 无 Token / 过期 / 伪造 |
| 403 | 是你，但你没资格 | 患者 A 查患者 B 的预约（对象级校验） |
| 404 | 没这货 | slot_id=99999 不存在 |
| 409 | 东西在，状态不允许 | 没号 / 重复预约 / 非法迁移 |

- 409 有两道防线：重复预约被**唯一约束**拦（数据库兜底），没号被**条件更新 affected=0** 拦（业务层判断）——同码不同层。
- 403 看身份，409 看状态；404 的进阶用法：公开接口可返回 404 防**资源枚举**，内部已认证接口用 403 讲清楚。

## 3. 权限模型：每个请求过两道门

1. **认证**：解 Token → 得到身份（401 层）；
2. **授权**：
   - 角色级：患者能抢号，管理员不能；
   - **对象级**：每一行数据问一次"这行是谁的"（排班 205 → schedule.doctor_id）。AI 生成代码最常漏掉的一层。

## 4. 三张事务时序图

### 4.1 创建预约（M4 总图纸）

```
患者APP        服务端              数据库
  │ POST /appointments(+幂等键)     │
  │──────────────→│ ①解析Token → patient_id
  │               │ ②查幂等键 → 已存在？返回原结果
  │               │ ③BEGIN
  │               │ ④UPDATE slot SET remaining=remaining-1
  │               │      WHERE id=501 AND remaining>0
  │               │      affected=0 → ROLLBACK → 409 没号
  │               │ ⑤INSERT appointment (PENDING, flag=1)
  │               │      撞唯一键 → ROLLBACK → 409 重复(④扣的号随回滚自动回来)
  │               │ ⑥INSERT history (NULL→PENDING)
  │               │ ⑦COMMIT
  │←──────────────│ 201 + 预约号
```

排序原则：事务内**先做最可能失败、决定后续有没有意义的步骤**（先扣号后插预约）。
事务边界：G(BEGIN) 与 D(COMMIT) 之间，C/A/F 三步在事务里；B/E（解析、查幂等）在事务外。

### 4.2 取消 vs 超时（竞争终态）

```
取消请求            数据库(行锁)           超时任务
   │ UPDATE...WHERE     │   UPDATE...WHERE   │
   │ status='PENDING'   │   status='PENDING' │
   │───────→ 同一行只一人成功 ←───────│
   │ affected=1 → 赢：同事务还号+写历史    affected=0 → 输：什么都不做
```

### 4.3 发布排班（发布也是 CAS）

```
医生APP        服务端               数据库
  │ POST /schedules/101/publish     │
  │──────────────→│ ①认证+对象级校验（101 是我的排班？不是→403）
  │               │ ②BEGIN
  │               │ ③UPDATE schedule SET status='PUBLISHED'
  │               │      WHERE id=101 AND status='DRAFT'
  │               │      affected=0 → 409 已发布/已停诊
  │               │ ④INSERT slot（生成号池）
  │               │ ⑤COMMIT → 200
```

CAS 第三次出现：扣号、取消/超时、发布——项目遗传密码。

## 5. 事务边界三规则

1. **包什么**：多写必须同生共死才包（④⑤⑥、③④）；单读单写自带原子性；
2. **不包什么**：数据库之外的一切（短信、HTTP 调用——回滚不了，且外部卡顿会捏着行锁拖垮全场）；
3. **划在哪**：一个事务 = 一个业务用例 = service 一个方法。

W7 种子：事务内外部调用的两条罪状 = 拖垮事务（行锁 30 秒）+ 幽灵消息（发了短信但回滚）。
解法哲学："想做的事先落库，提交后再兑现"（Outbox）。

## 6. DTO/VO

entity 是数据库的形状，DTO 是接口的形状，不混用。理由：安全（防敏感字段泄露）、解耦（表加列不动契约）、防事故（返回内容由 DTO 决定）。

## 7. 外键立场（学习者本人拍板，三段式）

> ① 不建外键约束，关联列只建普通索引；
> ② 预约创建是高并发热点路径：外键校验会在父行（slot）加 S 锁且持到事务提交，阻塞并发更新排队；且外键只校验存在性、不校验业务（remaining=0 依旧放行），业务规则反正要靠条件更新+唯一约束+状态机；
> ③ 代价是可能出现孤儿数据、删除无数据库保护——我接受：插入前应用层校验父记录、唯一约束防重复占用、删除/关闭父记录前先做业务校验、测试覆盖、定期对账。
